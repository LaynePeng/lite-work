# 辩论评审技能（多 Agent 对抗）

高风险决策、争议方案、关键代码的把关流程：生成 → 批判 → 修订循环，
直到批判者无法提出实质性问题（收敛）。

## 编排流程

### 第 1 步：生成/定位提案

- 已有方案：直接进入第 2 步
- 无方案：spawn proposer（role=general）产出初版方案，
  task 中写清需求、约束与验收标准

### 第 2 步：批判

spawn critic（role=critic，内置只读批判者角色），task 附上完整方案，
要求输出「问题清单（按严重度排序）：每项给出位置/影响/修改建议」。

### 第 3 步：对抗循环（2-3 轮为宜）

1. 批判意见送达后，followup_task 唤醒 proposer：
   「按以下批判意见修订方案，逐条说明采纳/拒绝及理由：{问题清单}」
2. 修订版完成后再 followup_task 唤醒 critic 复审：
   「复审修订版，只报告仍然存在的实质问题；无实质问题则明确输出
   [通过]」
3. critic 输出 [通过] 或轮次用尽 → 结束；否则回到第 1 步

补充：agent 仍在运行时不需要等它结束——send_message 可即时传达
澄清请求或补充材料（下轮生效）；followup_task 仅用于唤醒已完成的 agent。

### 第 4 步：裁决报告

你（主 Agent）输出最终裁决：采纳的方案 + 每轮修订的关键变化 +
未解决的分歧与你的取舍理由。裁决是你的职责，不要让两个 agent 自己收敛。

## 纪律

- 轮次上限 3 轮：多数争议第 2 轮已暴露本质，久拖是提示问题定义不清
- 分歧僵持时由你裁决，并在报告中明示「谁主张什么、你为何如此取舍」
- 代码审查场景：proposer 修订时可给 allowed_dirs 限定改动范围；
  critic 保持只读
- close_agent 释放完成的 agent
